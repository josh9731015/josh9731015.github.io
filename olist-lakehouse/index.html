電商資料湖倉：從原始檔到分析（Databricks）

余家丞 ｜ Olist 巴西電商公開資料 ｜ Databricks SQL、Delta Lake、Claude Code

本專案示範資料分析師如何「使用」資料湖倉（lakehouse，把原始檔案與整理好的資料表放在同一個平台管理）：把 9 個原始 CSV 檔放進 Databricks 雲端資料平台，依業界常見的三層架構整理成可以直接分析的表，沿途建立資料品質檢查，最後用整理好的表回答一個商業問題：「配送延遲會不會拉低顧客的評論分數？」資料是巴西電商平台 Olist 公開的約 10 萬筆訂單（2016-09～2018-10）。本專案以 AI 協作方式進行：SQL 由 Claude Code 協助撰寫，本人在 Databricks 逐段執行，並與本機用原始檔計算的答案核對；分析題目與頁面呈現由本人決定。

先說明資料的限制：顧客與賣家代號已匿名化，資料不代表 Olist 全部業績。本頁的分析是「晚到的訂單分數比較低」這類關聯，沒有做實驗，不能直接證明是延遲「造成」低分（見「限制」）。

結論：95,824 張已送達且有評價的訂單中，6.66% 晚於 Olist 給顧客的預計送達日。準時訂單平均 4.29 分；只晚 1～3 天就降到 3.29 分，晚 4 天以上降到 2.10 分以下，晚到 4 天以上的三組各有 67.68%～80.15% 給 1～2 星。這個落差不能用州別差異解釋：在晚到訂單較多的 14 個州（見分析二），州內晚到訂單都比準時訂單低 1.63～2.33 分。準時送達的訂單裡，等待天數越長分數也越低（等 0～7 天 4.41 分，等 31 天以上 3.62 分）。

建議：① 晚到的訂單只占 6.66%，但分數低很多，是值得優先處理的風險。建議每天列出「即將到預計送達日、仍未送達」的訂單，提前處理或主動通知顧客；通知是否真的能減少負評，需要用實驗驗證（見「若要繼續追查：需要的資料」）。② 準時率 93.2%（96,470 張已送達訂單中準時或提早的比例，含沒有評價的訂單）不等於顧客滿意：預計送達日抓得很寬（預計送達天數中位數 24 天，實際中位數 10 天），準時的訂單等越久分數仍越低，物流指標建議同時追蹤「實際配送天數」（見附錄）。

資料湖倉的三層架構

資料湖（data lake）是存放原始檔案的地方，什麼格式都能放，但不保證乾淨；資料倉儲（data warehouse）存放整理好、可以直接查詢的表。資料湖倉（lakehouse）把兩者放在同一個地方：原始檔與整理好的表都在 Databricks 裡，表使用 Delta Lake 格式，因此能做到一般檔案做不到的事，例如在寫入時擋下不合規的資料。資料由原始到可用分成三層，業界常稱為 medallion（獎牌）架構，類似餐廳處理食材：進貨原樣保存（bronze）→ 清洗、切好備料（silver）→ 依菜單組合成餐點（gold）。這樣分層的好處是：原始資料永遠留著，清洗出錯可以重來；每一層都能各自跑品質檢查。用一般的說法，這三層就是一個 ETL 流程（讀取、清洗、寫成分析用的表），gold 層則相當於給銷售分析用的 data mart。

bronze：先原樣保存，讀取時就發現兩個問題

bronze 層的原則是「不修改內容」，之後清洗出錯時，隨時可以從這一層重來。讀進來後立刻比對每張表的列數與原始檔，發現兩個讀取問題：

  • 評價留言含換行，一則評價被切成好幾列：用預設設定讀取（存成對照表 bronze_reviews_naive），評價表有 104,162 列，比原始檔的 99,224 則多出 4,938 列。加上「一筆資料可以跨好幾行」與「引號內的符號照原樣讀」兩項設定後，列數與原始檔一致。
  • 郵遞區號開頭的 0 不見了：系統把郵遞區號猜成數字，顧客表有 23,995 筆開頭的 0 被刪掉（例如 01310 變成 1310），會對不上座標表。讀取時指定郵遞區號欄位以文字讀入，顧客、賣家、座標 3 張 bronze 表都重建，重建後所有郵遞區號都是 5 碼。

silver：清洗規則——可疑的資料只標記，不刪除

建 silver 層前，先在 bronze 層數出每一種問題有幾列，再決定處理方式。可疑但可能是真實情況的資料（例如送達時間早於出貨時間）只加一個標記欄，不刪除，讓之後的分析自己決定要不要排除。

SQL：清洗規則怎麼寫（摘錄訂單、商品、評價 3 張表）
標記欄COALESCEROW_NUMBER 視窗函數
-- 訂單：一列都不刪，可疑的加標記欄
CREATE OR REPLACE TABLE workspace.olist.silver_orders AS
SELECT order_id, customer_id, order_status,
  order_purchase_timestamp, order_delivered_carrier_date,
  order_delivered_customer_date, order_estimated_delivery_date,
  -- 已送達卻沒有送達日
  (order_status = 'delivered' AND order_delivered_customer_date IS NULL) AS flag_delivered_no_date,
  -- 送達早於交給物流（任一日期是空值時記為 false）
  COALESCE(order_delivered_customer_date < order_delivered_carrier_date, false) AS flag_date_anomaly
FROM workspace.olist.bronze_orders;

-- 商品：品類有英文就用英文，沒有對照留葡萄牙文，沒有品類填 unknown
CREATE OR REPLACE TABLE workspace.olist.silver_products AS
SELECT p.product_id,
       COALESCE(t.product_category_name_english, p.product_category_name, 'unknown') AS category,
       p.product_weight_g
FROM workspace.olist.bronze_products AS p
LEFT JOIN workspace.olist.bronze_category_translation AS t
  ON p.product_category_name = t.product_category_name;

-- 評價：一列都不刪，每張訂單標出最後回覆的那一則
CREATE OR REPLACE TABLE workspace.olist.silver_order_reviews AS
SELECT review_id, order_id, review_score, review_comment_message, review_answer_timestamp,
  -- 同一張訂單依回覆時間排序，最新的一則為 true
  ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY review_answer_timestamp DESC) = 1 AS is_latest_for_order
FROM workspace.olist.bronze_order_reviews;

為了好讀，這裡只列分析會用到的欄位；實際的表還保留其他原樣帶過的欄位。

gold：星狀結構——一張事實表，四張維度表

gold 層依分析需求組合資料，常見做法是星狀結構：中間一張事實表記錄「發生了什麼」，本專案是 gold_fact_sales，一列代表「賣出的一件商品」（112,650 列），記價格與運費；周圍幾張維度表記錄「是誰、是什麼、在哪天」（顧客、商品、賣家、日期），查詢時用代號把它們接上事實表，例如用商品代號查出品類。日期維度表包含 2016-09-04～2018-10-17 每一天（774 天），沒有訂單的日子也有一列，按月彙總時才不會漏掉月份。

藍字＝用來接事實表的代號；Databricks 上的表名都有 gold_ 前綴。

5 張 gold 表都從 silver 層的表組出來，不回頭讀 bronze 或原始檔：

事實表的一列是「一件商品」（資料的最小單位，稱為粒度），所以本頁的配送分析不用這張表，而是回到 silver 層以「一張訂單」為單位：同一張訂單買 3 件商品，在事實表會有 3 列、3 列都帶著同一個評分，直接平均會讓多件訂單的評分被重複計算。

SQL：用星狀結構回答「2018 年營收最高的品類」
事實表 JOIN 維度表COUNT(DISTINCT)
SELECT
  p.category,
  ROUND(SUM(f.price), 2)               AS revenue,     -- 商品金額，不含運費
  COUNT(*)                             AS items_sold,  -- 事實表一列＝一件
  COUNT(DISTINCT c.customer_unique_id) AS buyers       -- 用「人」的代號計算買家數
FROM workspace.olist.gold_fact_sales AS f
JOIN workspace.olist.gold_dim_date     AS d USING (date_key)
JOIN workspace.olist.gold_dim_product  AS p USING (product_id)
JOIN workspace.olist.gold_dim_customer AS c USING (customer_id)
WHERE d.year = 2018 AND f.order_status = 'delivered'
GROUP BY p.category
ORDER BY revenue DESC
LIMIT 5;

年份依下單日計算；2018 年已送達的訂單，下單日只到 8 月底。結果第一名是 health_beauty（健康美容），營收 755,724.50 巴西雷亞爾。計算買家人數用 customer_unique_id（同一個人只有一個）；另一個欄位 customer_id 是每張訂單各給一個，同一人下兩次單會被算成兩人。

WARN 中有一條是「付款總額與商品＋運費不符（差超過 1 雷亞爾）」（比對 silver_order_payments 與 silver_order_items），共 249 張訂單，其中 232 張是付款多於商品＋運費。這 232 張有 98.7% 選擇分期付款（期數大於 1），金額相符的訂單用分期付款的只有 51.4%，多付的部分可能是分期利息，但資料無法證實；另外 17 張付款少於商品＋運費，原因不明。因此兩者都列為已知問題、不修改金額。

表上的「門禁」：哪些規則會在寫入時擋下壞資料

品質 VIEW 是資料寫進去之後才檢查；Delta 格式的表另外可以設定「寫入時就檢查」的規則，像大樓門禁，不合規的資料進不來。實際測試三種寫法：

寫法測試的表測試結果
CHECK 條件（評分 1～5）silver_order_reviews寫入一筆 6 分的評價被擋下，資料沒有寫入
CHECK 條件（評分至少 3）silver_order_reviews對已有 1、2 分評價的表加上這條規則加不上去：系統會先檢查現有資料，14,575 列違反
PRIMARY KEY 主鍵（宣告訂單編號不可重複）silver_orders寫入 2 筆相同編號的測試訂單沒有被擋，2 筆都寫入；Databricks 的主鍵只是說明用的標示，不會強制。品質 VIEW 的唯一性規則因此顯示 FAIL，測試資料隨後刪除

因此「不准重複」不能靠主鍵，要在寫入時處理：新資料用 MERGE（合併寫入）指令寫入，同一張訂單已存在就更新、不存在才新增。測試時也發現，如果同一批新資料裡同一張新訂單出現兩次，MERGE 會新增兩列，所以寫入前要先在新資料裡去重。

SQL：先去重再 MERGE
MERGE INTOQUALIFY ROW_NUMBER
MERGE INTO workspace.olist.silver_orders AS t
USING (
  SELECT * FROM VALUES
    ('TEST_NEW', 'shipped',   TIMESTAMP'2018-01-01 10:00:00'),
    ('TEST_NEW', 'delivered', TIMESTAMP'2018-01-05 10:00:00')
    AS v(order_id, order_status, updated_at)
  -- 同一張訂單只留最新的一列
  QUALIFY ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY updated_at DESC) = 1
) AS s
ON t.order_id = s.order_id
WHEN MATCHED THEN UPDATE SET t.order_status = s.order_status
WHEN NOT MATCHED THEN INSERT (order_id, customer_id, order_status)
  VALUES (s.order_id, (SELECT MIN(customer_id) FROM workspace.olist.silver_customers), s.order_status);

測試用的訂單借用一位既有顧客的代號，避免違反「訂單的顧客都在顧客表裡」這條規則；測試完已刪除，訂單表回到 99,441 列。

分析：配送延遲會不會拉低評論分數？

分析對象是狀態為「已送達」且有送達日的 96,470 張訂單（已送達 96,478 張，扣掉 8 張沒有送達日），其中有評價的 95,824 張（另 646 張沒有評價；同一張訂單有多則評價時只取最後回覆的一則）。定義：

  • 晚到天數＝實際送達日 − 預計送達日（只比日期，不比時間；0 或負數＝準時）
  • 平均分數＝該組評分加總 ÷ 該組訂單數；1～2 星比例＝給 1 或 2 星的訂單 ÷ 該組訂單數

SQL：同一州內比較
JOIN 三張 silver 表HAVING 篩選分組COUNT_IF
WITH scored AS (
  SELECT c.customer_state,
         DATEDIFF(CAST(o.order_delivered_customer_date AS DATE),
                  CAST(o.order_estimated_delivery_date AS DATE)) > 0 AS is_late,
         r.review_score
  FROM workspace.olist.silver_orders AS o
  JOIN workspace.olist.silver_order_reviews AS r
    ON o.order_id = r.order_id AND r.is_latest_for_order
  JOIN workspace.olist.silver_customers AS c ON o.customer_id = c.customer_id
  WHERE o.order_status = 'delivered' AND o.order_delivered_customer_date IS NOT NULL
)
SELECT customer_state,
       COUNT(*)                                            AS orders,
       ROUND(AVG(IF(is_late, 1, 0)) * 100, 2)              AS late_pct,
       ROUND(AVG(IF(NOT is_late, review_score, NULL)), 2)  AS ontime_score,  -- AVG 會略過 NULL
       ROUND(AVG(IF(is_late, review_score, NULL)), 2)      AS late_score,
       ROUND(AVG(IF(NOT is_late, review_score, NULL))
           - AVG(IF(is_late, review_score, NULL)), 2)      AS gap   -- 準時 − 晚到
FROM scored
GROUP BY customer_state
HAVING COUNT_IF(is_late) >= 100
ORDER BY gap DESC;

為什麼接著看這個：晚到的訂單通常也等得比較久。顧客給低分，可能是因為「沒有在說好的日期送到」，也可能只是「等太久」。兩者的改善方式不同：前者可以從預計送達日的設定著手，後者需要縮短實際配送時間。

SQL：等待天數 × 準時／晚到
兩個 DATEDIFF條件計數 COUNT_IF
WITH scored AS (
  SELECT DATEDIFF(CAST(o.order_delivered_customer_date AS DATE),
                  CAST(o.order_purchase_timestamp AS DATE))          AS wait_days,
         DATEDIFF(CAST(o.order_delivered_customer_date AS DATE),
                  CAST(o.order_estimated_delivery_date AS DATE)) > 0 AS is_late,
         r.review_score
  FROM workspace.olist.silver_orders AS o
  JOIN workspace.olist.silver_order_reviews AS r
    ON o.order_id = r.order_id AND r.is_latest_for_order
  WHERE o.order_status = 'delivered' AND o.order_delivered_customer_date IS NOT NULL
)
SELECT CASE WHEN wait_days <= 7  THEN '1 等 0-7 天'
            WHEN wait_days <= 14 THEN '2 等 8-14 天'
            WHEN wait_days <= 21 THEN '3 等 15-21 天'
            WHEN wait_days <= 30 THEN '4 等 22-30 天'
            ELSE                      '5 等 31 天以上' END AS wait_bucket,
       COUNT_IF(NOT is_late)                              AS ontime_orders,
       ROUND(AVG(IF(NOT is_late, review_score, NULL)), 2) AS ontime_score,
       COUNT_IF(is_late)                                  AS late_orders,
       ROUND(AVG(IF(is_late, review_score, NULL)), 2)     AS late_score,
       ROUND(AVG(IF(NOT is_late, review_score, NULL))
           - AVG(IF(is_late, review_score, NULL)), 2)     AS gap   -- 準時 − 晚到
FROM scored
GROUP BY wait_bucket
ORDER BY wait_bucket;

附錄：準時的訂單為什麼等越久分數越低？

分析三中，準時送達的訂單等越久分數越低。如果顧客依照預計送達日安排期待，準時的訂單應該不論等多久都差不多滿意。以下逐一檢查可能的解釋，每一項先寫出「如果成立，資料應該看到什麼」。

SQL：排除可能的解釋（只看準時訂單）
先彙總再 JOINUNION ALL 多組比較MEDIAN
WITH items AS (                    -- 先把訂單明細彙總成一張訂單一列
  SELECT i.order_id,
         COUNT(*)                    AS n_items,
         COUNT(DISTINCT i.seller_id) AS n_sellers,
         SUM(p.product_weight_g)     AS total_weight_g
  FROM workspace.olist.silver_order_items AS i
  LEFT JOIN workspace.olist.silver_products AS p ON i.product_id = p.product_id
  GROUP BY i.order_id
),
ontime AS (
  SELECT DATEDIFF(CAST(o.order_delivered_customer_date AS DATE), CAST(o.order_purchase_timestamp AS DATE)) AS wait_days,
         DATEDIFF(CAST(o.order_delivered_carrier_date AS DATE),  CAST(o.order_purchase_timestamp AS DATE)) AS seller_days,
         it.n_items, it.n_sellers, it.total_weight_g, r.review_score
  FROM workspace.olist.silver_orders AS o
  JOIN workspace.olist.silver_order_reviews AS r ON o.order_id = r.order_id AND r.is_latest_for_order
  LEFT JOIN items AS it ON o.order_id = it.order_id
  WHERE o.order_status = 'delivered' AND o.order_delivered_customer_date IS NOT NULL
    AND DATEDIFF(CAST(o.order_delivered_customer_date AS DATE),
                 CAST(o.order_estimated_delivery_date AS DATE)) <= 0
),
groups AS (                        -- 同一張訂單可以同時屬於好幾組
  SELECT '全部' AS grp, * FROM ontime
  UNION ALL SELECT '單件訂單',          * FROM ontime WHERE n_items = 1
  UNION ALL SELECT '總重 500 克以下',   * FROM ontime WHERE total_weight_g <= 500
  UNION ALL SELECT '賣家 2 天內交貨',   * FROM ontime WHERE seller_days <= 2
  UNION ALL SELECT '多賣家訂單',        * FROM ontime WHERE n_sellers > 1
)
SELECT grp, COUNT(*) AS orders,
       ROUND(AVG(IF(wait_days <= 7,              review_score, NULL)), 2) AS w0_7,
       ROUND(AVG(IF(wait_days BETWEEN 8  AND 14, review_score, NULL)), 2) AS w8_14,
       ROUND(AVG(IF(wait_days BETWEEN 15 AND 21, review_score, NULL)), 2) AS w15_21,
       ROUND(AVG(IF(wait_days BETWEEN 22 AND 30, review_score, NULL)), 2) AS w22_30,
       ROUND(AVG(IF(wait_days > 30,              review_score, NULL)), 2) AS w31_plus
FROM groups
GROUP BY grp;

-- 預計送達天數與實際送達天數
SELECT MEDIAN(DATEDIFF(CAST(order_estimated_delivery_date AS DATE), CAST(order_purchase_timestamp AS DATE))) AS promise_days_median,
       MEDIAN(DATEDIFF(CAST(order_delivered_customer_date AS DATE), CAST(order_purchase_timestamp AS DATE))) AS actual_days_median
FROM workspace.olist.silver_orders
WHERE order_status = 'delivered' AND order_delivered_customer_date IS NOT NULL;

上線監控

若把這個分析做成每日報表，建議監控兩件事：① 品質 VIEW 每天在資料更新後執行，任何一條 ERROR 規則失敗、或 WARN 規則的筆數超過門檻時發出警示，並暫停更新給分析用的 gold 層；② 每天列出「即將到預計送達日、仍未送達」的訂單數，並追蹤每月的晚到比例與實際配送天數中位數。

若要繼續追查：需要的資料
需要的資料可以判斷什麼
對晚到訂單主動通知或補償的實驗（隨機分組）延遲是否「造成」低分，以及通知能不能減少負評
顧客下單時看到的預計送達日與其他物流選項顧客的實際期待；縮短預計送達日是否會讓顧客更願意下單
每件商品各自的出貨與送達紀錄多賣家訂單分數低，是否因為分批送達
評價是在收貨後多久填寫、是否由平台主動邀請沒有評價的 646 張已送達訂單，是否和有評價的訂單一樣滿意

限制
  • 分析是觀察資料的關聯。晚到的訂單可能同時有其他問題（例如商品缺貨後補寄），低分不一定只來自延遲；同州比較只排除了地區這一個因素。
  • 只分析有評價的已送達訂單（95,824 張）；取消、未送達的訂單沒有送達日，不在分析範圍內。
  • 晚到天數只比日期；當天晚上送達也算準時。
  • 留言關鍵字只抓「demor」一種寫法，屬於粗略計算，只能看趨勢。
