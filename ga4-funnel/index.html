電商網站轉換漏斗分析（BigQuery SQL）

余家丞 ｜ Google 官方 GA4 電商範例資料 ｜ BigQuery SQL、Claude Code

本專案以 SQL 回答電商常見的問題：「網站訪客在購買流程的哪一步流失最多？」購買流程分成「看商品 → 加入購物車 → 開始結帳 → 購買」四步，每往下一步人數就變少，形狀像漏斗，因此稱為轉換漏斗。資料是 Google 官方周邊商品網路商店的網站行為紀錄，由 Google 的網站分析工具 GA4（Google Analytics 4）記錄。本專案以 AI 協作方式進行：SQL 由 Claude Code 協助撰寫，分析範圍與頁面呈現由本人決定，並逐段檢視每個查詢的邏輯與中間結果。

先說明資料的限制：為保護隱私，Google 把這份資料的部分內容改成替代值（例如「(not set)」），官方也說明資料前後可能對不上，因此人數與金額不能當成真實業績；期間涵蓋黑色星期五與聖誕節，不代表平常月份。本頁的重點是示範「如何用 SQL 建立漏斗，並在過程中檢查資料品質」。

45,107分析期間看過商品的使用者
6.11%按照順序走完四步並購買的比例（2,755 ÷ 45,107）
26.6%看過商品後加入購物車的比例（12,016 ÷ 45,107），各步中最低

結論：2020-11-26～2021-01-31 看過商品的 45,107 位使用者中，6.11% 依序完成四個步驟並購買。流失最多的一步是「看商品→加入購物車」：轉換率 26.6%（走到這一步的人數 ÷ 走到上一步的人數），流失 33,091 人，用多種算法重新檢查（見分析三、四），它都仍是三個轉換中最低的。另外，依序走完四步的 2,755 位購買者中，92.4% 從某一次看商品到購買的每一步都在 30 分鐘內完成：購買前的最後一段流程多半是連續完成的（使用者在這之前是否考慮過好幾天，這個算法看不出來）。

建議：① 目前沒有比較基準判斷 26.6% 是否偏低；下一步可依裝置、流量來源分組比較，找出明顯偏低的族群，再搭配商品頁的互動資料找原因（見「若要繼續追查：需要的資料」）。② 購買前的最後一段流程多半在短時間內連續完成，購物車與結帳流程應以當下操作的順暢為主（見分析三）。③ 「加入購物車」事件在 2020 年 11 月有多天沒有紀錄（見「資料品質檢查」第 1 項），真實環境中應先查追蹤設定，並建立每日監控（見「上線監控」）。

資料品質檢查

建立漏斗前，先檢查這四種事件的紀錄。11-26 之後每天都有「看商品」與「購買」的紀錄（分別為每天至少 1,390 筆、14 筆，依每日筆數統計）；以下四項中，第 1、4 項改變了漏斗的算法，第 2、3 項只影響營收的計算（漏斗算的是人數）。

1. 「加入購物車」在 11 月有 18 天沒有紀錄 → 分析期間從 11-26 開始

2020-11-02～11-15 與 11-21～11-24 共 18 天，「加入購物車」每天 0 筆，但同一期間「開始結帳」每天 132～605 筆。這不太可能是沒有人加入購物車，原因可能是追蹤缺漏，也可能是範例資料的處理方式，無法從資料區分。11-25 起恢復紀錄（之後每天 229～2,135 筆）。11-25 是恢復的第一天，無法確定當天是否整天都有記錄，保守起見，分析從隔天 11-26 開始（11-01 與 11-20 筆數也很低，同樣在排除範圍內）。

2. 15.9% 的購買事件沒有訂單編號 → 計算營收時排除，計算人數時保留

全部 5,692 筆購買事件中，訂單編號為 (not set) 的有 883 筆、空值（NULL）的有 23 筆，合計 906 筆（15.9%）。其中 456 筆仍有大於 0 的購買金額，編號被替代值取代不代表沒有購買；漏斗計算人數用不到訂單編號，因此保留這些事件；計算營收時則需要依訂單編號合併重複紀錄，才排除這些事件（見下一項），因此下一項的營收是下限。若漏斗也排除這些事件，購買人數會從 2,755 變成 2,489，「開始結帳→購買」從 57.4% 變成 51.8%。

補充：「不同使用者出現同一個編號」為什麼多出 3 筆？

15 個編號各被 2 位使用者用到，實際是 15 × 2 ＝ 30 張訂單，但共被記錄 33 次，33 − 30 ＝ 3 次是其中一位使用者自己重複送出。例如訂單 140428：

使用者時間金額說明
70837463…2020-11-23 20:40:09.57413A 的訂單
70837463…2020-11-23 20:40:09.60613A 重複送出（多出的 1 筆）
86949711…2020-12-18 15:28:10.97227B 的另一張訂單

因此去重時以「使用者＋訂單編號」為單位：刪掉 A 重複的那一筆，但保留 B 的訂單。

同一使用者、同一訂單編號的重複紀錄只保留一筆（同一使用者重複送出的 314 組紀錄〔表中 311 組，加上「不同使用者出現同一個編號」中的 3 組〕，每組各筆金額都相同，保留哪一筆不影響營收），刪掉多出的 320 筆後剩 4,466 筆，營收從 330,348 美元變成 308,830 美元；不處理會多算 7.0%（330,348 ÷ 308,830 − 1）。這 15 個編號中，每個編號的兩位使用者購買日期與金額都不同，較可能是替代值造成的編號重複，因此視為不同訂單、不合併。漏斗計算的是人數，不受這一項影響。

SQL：以「使用者＋訂單編號」去重
視窗函數 ROW_NUMBERQUALIFYCTE
WITH p AS (
  SELECT ecommerce.transaction_id AS tx, user_pseudo_id, event_timestamp,
         ecommerce.purchase_revenue AS revenue
  FROM `bigquery-public-data.ga4_obfuscated_sample_ecommerce.events_*`
  WHERE event_name = 'purchase'
    AND ecommerce.transaction_id != '(not set)'  -- 空值在這個比較下也會被排除
  -- 同一使用者、同一訂單編號只留一筆（重複紀錄金額相同，依時間排序只為結果固定）
  QUALIFY ROW_NUMBER() OVER (PARTITION BY user_pseudo_id, ecommerce.transaction_id ORDER BY event_timestamp) = 1
)
SELECT COUNT(*) AS n_rows, ROUND(SUM(revenue)) AS revenue
FROM p;

4. 部分「看商品」與「加入購物車」的時間完全相同 → 同時也算有順序

分析期間有 6,569 位使用者（佔走到「加入購物車」的 12,016 人的 54.7%），至少有一次「看商品」和「加入購物車」的時間完全相同。依 Google 官方說明，網頁版的事件時間是 Google Analytics「收到」事件的時間，同一次傳送的多個事件會共用同一個時間，所以無法從時間分出先後（2024 年之後的 GA4 資料另有記錄批次內順序的欄位，這份 2020 年的資料沒有）。若規定後一步必須「晚於」前一步，走到「加入購物車」的人數會從 12,016 人變成 11,535 人，少算 481 人，因此本分析把「同時」也視為依序發生。

分析

分析一：每一步各有多少人做過

先照問題的字面，計算分析期間內做過每一種事件的人數（結果列在分析二表格的「沒順序」欄）。這個算法只看「期間內有沒有做過」，不看先後：先結帳、隔天才看商品的人，也會被算進第 3 步（開始結帳）。結果：看商品 45,107 人、購買 3,351 人，整體 7.43%（完整數字見分析二表格「沒順序」欄）。

結論：不檢查順序時整體轉換率為 7.43%，但這個數字包含沒有依序走完的人，需要再加上順序檢查。

SQL：一次掃描算出四步人數
條件聚合 COUNT(DISTINCT IF(...))_TABLE_SUFFIX 篩選日期
SELECT
  COUNT(DISTINCT IF(event_name = 'view_item',      user_pseudo_id, NULL)) AS s1_view_item,
  COUNT(DISTINCT IF(event_name = 'add_to_cart',    user_pseudo_id, NULL)) AS s2_add_to_cart,
  COUNT(DISTINCT IF(event_name = 'begin_checkout', user_pseudo_id, NULL)) AS s3_begin_checkout,
  COUNT(DISTINCT IF(event_name = 'purchase', user_pseudo_id, NULL)) AS s4_purchase
FROM `bigquery-public-data.ga4_obfuscated_sample_ecommerce.events_*`
WHERE event_name IN ('view_item', 'add_to_cart', 'begin_checkout', 'purchase')
  AND _TABLE_SUFFIX >= '20201126';

為什麼接著看這個：沒有檢查順序時，跳著走的人會被算進後面的步驟，第 2～4 步的人數都會被高估。

不檢查順序時，「加入購物車→開始結帳」看起來高於「開始結帳→購買」（54.1% 對 51.5%）；檢查順序後則是 40.0% 對 57.4%，判斷相反。

結論：加上順序後，流失最多的仍是「看商品→加入購物車」（26.6%，流失 33,091 人）；順序檢查會改變後兩步的高低判斷，因此之後的分析一律使用有順序的版本。

補充：沒有加入購物車紀錄就結帳的人，是不是更早就加入購物車了？

1,639 人中有 1,141 人在 92 天內完全沒有加入購物車的紀錄。一種可能是他們更早就把商品加入購物車（11-01 之前，或 11 月沒有紀錄的那幾天），考慮一段時間才回來結帳。如果是這樣，他們的結帳時間應該集中在分析期間前段。

SQL：有順序的漏斗
CTE 串接非等值 JOIN（ON 條件含 >=）MIN + GROUP BY
WITH ev AS (
  SELECT user_pseudo_id AS user, event_name, event_timestamp AS ts
  FROM `bigquery-public-data.ga4_obfuscated_sample_ecommerce.events_*`
  WHERE event_name IN ('view_item', 'add_to_cart', 'begin_checkout', 'purchase')
    AND _TABLE_SUFFIX >= '20201126'
),
s1 AS (  -- 每人第一次看商品的時間
  SELECT user, MIN(ts) AS t1 FROM ev WHERE event_name = 'view_item' GROUP BY user
),
s2 AS (  -- 看商品之後（含同時），第一次加入購物車的時間
  SELECT s1.user, MIN(ev.ts) AS t2
  FROM s1 JOIN ev
    ON ev.user = s1.user AND ev.event_name = 'add_to_cart' AND ev.ts >= s1.t1
  GROUP BY s1.user
),
s3 AS (
  SELECT s2.user, MIN(ev.ts) AS t3
  FROM s2 JOIN ev
    ON ev.user = s2.user AND ev.event_name = 'begin_checkout' AND ev.ts >= s2.t2
  GROUP BY s2.user
),
s4 AS (  -- 開始結帳之後有購買的人（每人一列）
  SELECT DISTINCT s3.user
  FROM s3 JOIN ev
    ON ev.user = s3.user AND ev.event_name = 'purchase' AND ev.ts >= s3.t3
)
SELECT
  (SELECT COUNT(*) FROM s1) AS s1_view_item,
  (SELECT COUNT(*) FROM s2) AS s2_add_to_cart,
  (SELECT COUNT(*) FROM s3) AS s3_begin_checkout,
  (SELECT COUNT(*) FROM s4) AS s4_purchase;

每一步都取「上一步第一次發生之後最早的一次」。不限時間時，從最早的一次開始接，能接上的機會最大，所以這個寫法不會漏算。

為什麼接著看這個：分析二只要求「之後」發生，相隔兩個月也算。間隔太久的動作可能與當初的瀏覽無關，例如兩個月前看過、這次因為看到廣告才回來購買，算進同一條流程會高估轉換率。實務上的漏斗報表通常會設定時限（GA4 的漏斗報表也提供「在幾分鐘／幾天內完成下一步」的設定），而時限要依想回答的問題選擇。因此用 30 分鐘、24 小時、7 天三種時限各算一次，分別回答不同的問題，並與不限時間（分析二）比較，確認結論是否改變。

分析三：限定每一步在上一步之後多久內完成

規則：每一步都必須在上一步之後的限定時間內完成（例如 30 分鐘內加入購物車、再 30 分鐘內開始結帳）。使用者看過商品好幾次時，任何一次都可以當起點；因此這裡量的是「從某一次看商品到購買」這一段，看不出使用者在那之前考慮了多久。

24 小時每一步隔了一段時間（但在 24 小時內）才完成的人有多少（整段最長 3 天）購買 2,682 人，比 30 分鐘多 136 人；整體 5.95%24 小時內完成購買的人中，94.9%（2,546 ÷ 2,682）每一步都在 30 分鐘內完成，隔一段時間才完成某一步的很少
7 天每一步隔了幾天才完成的人有多少（整段最長 21 天）購買 2,726 人，比 1 天只多 44 人；整體 6.04%每一步隔了幾天才完成的情況很少；但使用者在第一次看商品後考慮多久，這個算法看不出來

結論：時限不改變三個轉換的高低順序；依序完成的購買中，購買前的最後一段流程多半是連續完成的（每一步都在 30 分鐘內：92.4%）。

因此改善購物車與結帳流程時，應以使用者當下操作的順暢為主。這個發現有三個限制：① 只涵蓋依序走完四步的 2,755 位購買者，另外 596 位購買者（3,351 − 2,755）沒有依序走完，無法判斷；② 看不出使用者在最後一次看商品之前考慮了多久；③ 使用者換裝置、清除 cookie 或使用無痕視窗會變成新的代號，跨天回來的流程可能被切斷。寄送提醒能否把人帶回來，這份資料沒有相關紀錄，無法判斷。

SQL：一次計算四種時間限制
UNNEST 自訂清單CROSS JOIN非等值 JOIN（時間區間）SELECT DISTINCT

接在分析二的 WITH ev AS (...) 之後（以逗號接續）。r2 找出「在某一次看商品之後 w 分鐘內」的加購事件，r3、r4 再從這些事件往下接，所以每一段的起點都可以是任何一次上一步。

wins AS (SELECT win FROM UNNEST([30, 60 * 24, 60 * 24 * 7, 999999]) AS win),  -- 分鐘；999999 ≈ 不限
v AS (SELECT DISTINCT user, ts FROM ev WHERE event_name = 'view_item'),  -- 同一時間的重複看商品只留一筆，避免下面 JOIN 列數暴增
r2 AS (
  SELECT DISTINCT wins.win, c.user, c.ts
  FROM ev c CROSS JOIN wins
  JOIN v ON v.user = c.user AND v.ts <= c.ts AND c.ts - v.ts <= wins.win * 60 * 1000000  -- 分鐘換成微秒
  WHERE c.event_name = 'add_to_cart'
),
r3 AS (
  SELECT DISTINCT r2.win, k.user, k.ts
  FROM ev k JOIN r2
    ON r2.user = k.user AND r2.ts <= k.ts AND k.ts - r2.ts <= r2.win * 60 * 1000000
  WHERE k.event_name = 'begin_checkout'
),
r4 AS (
  SELECT r3.win, p.user
  FROM ev p JOIN r3
    ON r3.user = p.user AND r3.ts <= p.ts AND p.ts - r3.ts <= r3.win * 60 * 1000000
  WHERE p.event_name = 'purchase'
)
SELECT win,
  (SELECT COUNT(DISTINCT user) FROM v) AS s1_view_item,
  n2.n AS s2_add_to_cart, n3.n AS s3_begin_checkout, n4.n AS s4_purchase
FROM (SELECT win, COUNT(DISTINCT user) AS n FROM r2 GROUP BY win) n2
JOIN (SELECT win, COUNT(DISTINCT user) AS n FROM r3 GROUP BY win) n3 USING (win)
JOIN (SELECT win, COUNT(DISTINCT user) AS n FROM r4 GROUP BY win) n4 USING (win)
ORDER BY win;

為什麼接著看這個：分析二的拆解中，有 1,639 人在看商品之後開始結帳，卻沒有走完「看商品→加入購物車→開始結帳」的順序。原因可能是「加入購物車」事件漏記，也可能是網站有不經過購物車的結帳方式；若是漏記，「加入購物車→開始結帳」的轉換率就會被低估，因此檢查結論對這個問題有多敏感。

第 3 類開始結帳後只有 8 人購買，行為與第 1 類差異很大，較不像漏記，所以「全部補回」只當作上限參考。這項檢查也只能補回「之後有開始結帳」的漏記：漏記了加入購物車、之後也沒有結帳的人，在資料中看不出來。

BigQuery 查詢成本

BigQuery 的隨選（on-demand）方案依每次查詢處理的資料量計費。這一節示範兩種常見的省錢做法對處理量的影響（使用簡化的查詢，不是上面的漏斗查詢）。本專案另外測試了兩種常見的省錢做法：依日期「分區」（把表按日期分格，只讀需要的日期）與依欄位「叢集」（把同類資料排在一起，只讀相關區段）。本次測試中，篩選條件剛好是分區或叢集所用的欄位時（例如依日期分區、篩 92 天中的 7 天），處理量減少約 90%。

測試方法與結果

處理量由「讀了哪些欄位」與「讀了哪些日期」決定；實際計費另有下限（每次查詢、每張被查詢的表最少以 10 MB 計），資料量小時計費金額會高於下表的處理量。本專案在練習帳號中建立三張內容相同（4,295,584 列、211.5 MB）、儲存方式不同的表，用兩個查詢比較處理量：查詢 A 計算 2020-12-01～12-07 的不重複使用者數，查詢 B 計算有 purchase 事件的不重複使用者數。

限制
  • 使用者以瀏覽器為單位（user_id 全部為空值），同一人跨裝置會被算成不同人。
  • 漏斗以「人」為單位，不限定同一商品或同一次造訪：看了 A 商品、之後把 B 商品加入購物車，也算往下走了一步。因此轉換率通常會高於以「單次造訪」計算的轉換率，兩者不能直接比較。
  • 資料在 2021-01-31 結束：越接近結束日才開始的流程，越可能來不及走完，各種時間限制下的轉換率都可能略為低估。漏斗人數不納入 11-26 之前的行為（分析四分類時例外）。

② 先從新訪客下手新訪客有 41,920 人，佔看過商品的人 93%，人數最多、改善空間最大；他們看過商品後加入購物車的比例，比同一時期第一次出現的舊訪客低 7～12 個百分點；但舊訪客本身購買意願較高，改版對新訪客的成效需以 ③ 驗證
③ 改版前先做 A/B 測試網站同時保留兩個版本，依新訪客的瀏覽器代號隨機分組（同一瀏覽器每次看到同一版）：對照組看現在的商品頁，實驗組看改版後的，比較兩組的「看商品→加購」轉換率。要偵測新訪客的轉換率從 25.8% 升到 27.8%，每組約需 7,700 人（顯著水準 5%、檢定力 80%）；兩組合計約 15,400 人，以資料期間平均每天約 630 位新訪客計，實驗約需跑 25 天，淡季流量較少時會更久
④ 建立每日事件數監控任何一種漏斗事件降為 0 就發警示；11 月加購有 18 天沒紀錄，建立監控即可在當天發現

查詢成本控制

BigQuery 依處理量計費：篩選條件用哪個欄位，就用那個欄位分區或叢集，處理量可減少約 90%；資料到 TB 級時，少讀 90% 就等於費用少 90%
