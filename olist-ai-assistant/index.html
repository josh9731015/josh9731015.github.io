AI 資料助理：用評估驅動開發的 LLM 應用

余家丞 ｜ Olist 巴西電商公開資料 ｜ Python、Gemini API、DuckDB、Streamlit、Claude Code

本專案示範如何讓大型語言模型（LLM，像 ChatGPT、Gemini 這類能讀寫文字的 AI）做成的資料助理輸出可以被驗證：AI 寫出的數字和引用由程式核對，對不上的地方會標出來；每個功能都有可重跑的自動評分。營運主管用中文提問，系統有 4 個功能：

  • 問資料：AI 自己寫 SQL（查資料庫用的語言）查資料並回答
  • 評論分類：把每則負評歸到固定的 10 個類別（例：送貨太慢、商品品質問題、跟描述不符）
  • 找相關評論：輸入一個問題，從評論中找出相關的幾則當證據並寫總結
  • 調查：依固定流程呼叫分析工具，調查「為什麼某些州的差評（1～2 星）比較多」

重點不在資料分析的發現，而在 AI 工程：流程、評估、可靠性與成本。資料沿用 Olist 約 10 萬筆訂單（2016-09～2018-10，資料介紹見「電商資料湖倉」頁）。分工：需求、指標定義、驗收標準與驗收由本人決定；程式由 AI 寫程式工具 Claude Code 撰寫，本人審查並以使用者角度驗收。

先說明兩種題目：「練習題」是開發時反覆拿來調整的題目，分數容易偏高；「新題目」是開發時沒拿來調整的題目，比較能代表真實水準。

限制：每項只有 19～50 題（則），「調查」練習題、新題目各只有 1 題；題量小，誤差可達十幾個百分點以上（例：評論分類 22/25，真實準確率可能落在 70%～96%）；其他限制見「限制與下一步」。

19/19「問資料」練習題通過題數（沒有新題目，成績可能偏高）
20/20「找相關評論」新題目盲測，AI 判斷相不相關與本人一致的則數
22/25「評論分類」新題目盲測，與本人完全一致的則數（88%，未達 90% 門檻）
4/4「調查」最終版跑 4 次，17 項檢查全過的次數（新題目 2 次也全過）

結論：可靠性來自分工：AI 只負責理解問題和寫出文字，數字、日期、規則判定、評論原文由程式產生或核對，對不上就標示出來。4 項成績中只有「評論分類」未達門檻；「問資料」沒有新題目，成績可能偏高。

工作流程
  1. 先定義成功標準：每個功能動手前先寫需求與驗收門檻；營收、準時、差評等指標的算法寫成一份「資料表說明」文件，AI 與人都照它計算。
  2. 評估驅動開發（每次修改都自動重跑評分）：每發現一種錯誤，就變成一條會自動重跑的檢查；修改後重跑，確認沒有退步。
  3. 換題盲測（防止只會背題目）：開發時反覆使用的「練習題」分數會越調越高，因此另外保留開發時沒拿來調整的「新題目」量真實水準：評論分類、找相關評論的新題目由本人先判斷，判斷時看不到 AI 的答案（盲測）；「調查」的新題目是同一題型換一州，由程式評分，開發中也重跑過，只用來確認沒有退步，沒有依它的結果修改程式；「問資料」沒有新題目。標準答案不放進給 AI 的指示，並用程式自動掃描指示裡有沒有答案。
  4. 本人驗收：評論分類的類別界線、評論相不相關由本人判斷（少數依本人定的規則自動套用），AI 的成績是跟本人的判斷比出來的；問資料、調查的標準答案是 Claude Code 寫的 SQL，由本人審查指標定義。
  5. 獨立審查：另開沒看過專案的 AI 審查者，只找「數字算錯」與「會讓使用者做錯決定的結論」，每項附 SQL 與查詢結果，核對後才修改；「調查」共 6 輪，問題從數字錯誤收斂到結論措辭才停止。
  6. 以使用者角度試用：本人以營運主管的角度實際操作網頁，找出「程式正確、但主管看不懂或會誤會」的問題，優先改成程式機制或固定測試題，不只靠提醒 AI 注意。

系統架構

4 個功能的原則相同：AI 負責理解文字與寫出文字，能用程式計算或檢查的交給程式。

功能AI 負責程式負責
問資料把中文問題寫成 SQL；把查詢結果寫成白話回答SQL 護欄（只允許讀取、逾時、列數上限）；核對回答裡的數字都出現在查詢結果中（排名用語、星等、門檻條件除外），對不上就標示 ⚠️。只保證數字有出處，SQL 是否寫對由評分檢查
評論分類從固定類別清單中挑類別（輸出格式被規定，不能自創類別）「送貨太慢」「沒收到貨」「訂單被取消或缺貨」改由程式依訂單日期與狀態判斷
找相關評論（RAG：先找資料、再根據資料回答）改寫問題；逐則判斷評論是否相關並寫理由；只用相關評論寫總結，每個重點標出處用本機向量模型（把文字轉成可比較意思的數字）找出意思相近的評論，不花 API 額度；附上每筆訂單的送達紀錄
調查（agent：AI 呼叫工具完成任務；為了穩定，大部分步驟由程式決定）在程式限定的範圍內決定工具呼叫順序、讀工具結果、照固定格式寫報告6 個工具（總覽、全州比較、單州深入、評論分類、找評論、SQL 查詢）算好數字與 4 個假說（配送延遲、時間、品類、賣家）的判定，要深入哪幾州由程式指定；評論原文、判定、「預期看到什麼」（假說成立時資料應該看到的結果）由程式填入；不是調查題就轉給「問資料」

模型：網頁和評分用同一組 Gemini 免費模型；網頁額度用完時自動換備援模型，評分時鎖定單一模型、不換備援；問資料、調查、評論分類會記錄實際回答的模型版本（模型名稱見頁尾）。

「問資料」：回答上方標出數字是否都有根據，展開可看 AI 執行的 SQL 與查詢結果

設計上的防呆：「調查」的 AI 結論寫「物流因素皆能解釋大部分的差距」，下方「程式依工具判定附註」更正為只能解釋部分差距

評估方法與成績
功能練習題新題目評估什麼、怎麼評
問資料19/19 題—17 題的標準答案用另一段 SQL 現算（由 Claude Code 另外撰寫、本人審查定義），數字要一致且有根據；2 題要回答「資料裡沒有」。19 題在開發中也被用來調整，沒另外保留新題目；給 AI 的指示經程式掃描、不含標準答案
找相關評論45/50 則20/20 則只評「判斷評論相不相關」這一步，不含搜尋有沒有漏找；相關、不相關分開算抓對比例
評論分類27/30 則舊版22/25 則新題目：一則評論可以有多個類別，AI 的類別組合跟本人完全一致才算對；由程式判定的 3 類（送貨太慢、沒收到貨、訂單被取消或缺貨）不列入比對，分母仍是 25 則；新題目原有 30 則，其中 5 則被拿來補定義，只用其餘 25 則計分。練習題：舊版定義與不同模型的成績（中間又改過 3 版），本人判對錯（27 則判對中有 7 則由 Claude Code 依本人定的規則套用），現行版沒有重新驗收
調查4/4 次全過2/2 次全過練習題「為什麼某些州差評多」每次跑 17 項檢查；新題目「為什麼 CE 州（Ceará）差評多」跑其中 6 項通用檢查（數字、根據、引用、判定、格式、呼叫上限），其餘 11 項只適用練習題（例：有沒有點名差評率最高的州）。「全過」看的是最終報告：4 次中 1 次初稿格式不符，被程式退回重寫一次後通過
  • 找相關評論：練習題相關的 34 則抓到 32 則（94%）、不相關的 16 則排除 13 則（81%），只到及格；新題目 2 題共 20 則（每題取搜尋結果前 10 則、未挑選；相關 10、不相關 10）全部判斷正確，達標。新門檻在跑新題目之前就定好，但它是看到練習題分數後才訂的：原本的門檻「50 則對 47 則」是 Claude Code 自訂、沒有依據，練習題沒過後，改照驗證 AI 評分器的常見做法，相關、不相關分開算抓對比例，兩者都 > 90% 達標、相關 > 80% 為最低線；不相關的及格線 ≥ 75% 由本人另訂。因此練習題的「及格」只能參考，新題目的「達標」才算數。
  • 評論分類：新題目 25 則，定義和模型一起更換前後都是 22/25，錯的題目換了 1 則，沒有進步（兩者一起換，分不出各自的效果）。其中 1 則在看過 AI 答案後更正了本人答案（當時畫面沒顯示評論日期），用原答案算是 21/25。
  • 調查的穩定度：調查的主流程每次都重新呼叫 AI。修改過程中多次失敗（引用被改字、判定抄錯、撞到呼叫上限），每種都改成程式處理或加上檢查後，最終版跑 4 次全部通過。評分程式本身也出過錯：曾把句子裡後一州的差評率算到前一州（報告本身正確），改正後重評練習題全部 50 筆紀錄，只有這類誤判 2 筆改判，並補上刻意造錯的測試，確認真的錯誤仍會被抓到。

可靠性：抓到的問題與解法

每個問題都往根本原因修：能交給程式的就交給程式，而不是在給 AI 的指示裡多加一句「請注意」。

問題怎麼發現解法
AI 引用評論時改了日期（11/09 抄成 09/09）程式逐字比對AI 只寫評論代碼，原文由程式貼上
給 AI 的指示中，範例剛好是標準答案流程檢討、獨立審查「調查」和「問資料」都發生過（「資料表說明」的範例寫出了 19 題中 11 題的答案或答法）；範例裡的真實答案改成代稱，並加程式自動掃描給 AI 的指示與工具說明；頁面上的成績都是修正後重跑的
額度用完時模型被自動換掉，一輪分數混了兩個模型事前檢討評分時鎖定模型，並記錄實際回答的模型版本
報告把只能解釋一半差距的原因寫成主因獨立審查程式依工具判定，在結論補上附註
查 3 個州剛好用掉 20 次工具呼叫上限工具呼叫紀錄一州的 4 個假說合成 1 個工具，最終版每次 7～11 次
「預期看到什麼」與實際檢查方法對不上；每次報告段落結構不同使用者驗收預期說法由程式寫好照填；固定報告格式，不符就退回
使用者要自己判斷該到哪個功能提問使用者驗收調查功能遇到查詢題，自動轉給「問資料」回答
「問資料」和「調查」算出不同的聖保羅州（SP）差評數（含取消與缺貨訂單 5,242 則、不含 4,750 則）使用者驗收統一採用含取消與缺貨的算法（取消本身就是不滿的原因），寫進資料表說明並加成固定測試題

成本與營運
  • 呼叫次數就是成本：免費版每個模型每天 20～500 次請求；「問資料」一題通常 2 次請求（寫 SQL、寫回答各 1 次）；調查練習題最終版每次用 7～11 次工具呼叫（上限 20 次，被退回重寫時最多再 6 次），一次約 12～18 秒；碰到每分鐘上限時會等待重試，第一次替某州評論分類也要多花幾十秒。
  • 回應快取：分類、相關判斷這類固定答案的步驟，輸入完全相同就不重問；調查把各州的評論分類結果存檔重用，分類定義或模型一改就重新分類。
  • 用自己的題目選模型：公開排行榜沒有「判斷葡萄牙文評論」這類任務，因此用「找相關評論」的 50 則練習題比較候選的免費模型（5 個中只有 2 個跑出分數：46/50、37/50，其餘當日額度用完或回傳格式不符），選分數較高的一個，評論分類也用同一個模型（沒有另外在分類上比較）；之後收窄「客服問題」類別的定義（相關判斷也引用同一份類別定義）重跑，成績表的 45/50 是現行版。
  • 紀錄：每次提問留下問題、SQL、模型版本、工具呼叫與失敗原因（每分鐘或每天的上限），網頁可逐步回放調查過程。

限制與下一步
  • 調查功能只支援一種題型：目前只能調查「各州差評原因」；其他「為什麼」的問題轉給「問資料」回答，原因說明標明「AI 推論，未經假說檢驗」。下一步是通用調查：任何問題都走「假說 → 預期 → SQL 查 → 程式判定」。
  • 評論分類未達標：補定義沒有讓新題目進步，再加規則效益很低；下一步是精簡定義，再用另一批新題目量。
  • 問資料沒有新題目：問資料的 19 題在開發中也被用來調整，成績可能偏高。
  • 標準答案和系統出自同一個 AI：問資料的標準答案 SQL 與系統都由 Claude Code 撰寫，可能犯同類錯誤；本人審查了指標定義，但沒有逐行獨立重寫。獨立審查者也是同一系列模型，可能有同樣的盲點。
  • 題量小、只有一位判斷者：找相關評論的不相關評論練習題只有 16 則，評論相關與分類的判斷只有本人一位，沒有第二位判斷者比對一致程度。
  • 找相關評論只評了判斷這一步：沒有量向量搜尋是否漏找相關評論，也沒有評總結是否忠於原文。
  • 使用免費預覽版模型：Google 可能隨時調整；網頁額度用完時換上的備援模型沒有用現行版本評分過。正式上線要改用付費版並固定模型版本。
  • 評分程式只有部分檢查有測試：數字根據、引用比對、州與差評率這幾項有刻意造錯的測試，其餘檢查沒有；10-23 就曾發現一個誤判。

工具：Python（google-genai、DuckDB、Streamlit、fastembed）、Gemini API 免費版、Claude Code。資料：Olist Brazilian E-Commerce Public Dataset（Kaggle）。成績日期：問資料、調查 2026-10-23；找相關評論、評論分類 2026-10-22。

模型：問資料與調查 gemini-3.5-flash-lite（備援 gemini-3.5-flash）；評論分類與相關判斷 gemini-3.1-flash-lite-preview（2 個跑出分數的模型中，50 則練習題分數較高；備援 gemini-3.5-flash-lite）；找相關評論的總結 gemini-3.5-flash-lite；向量模型 paraphrase-multilingual-MiniLM-L12-v2。
